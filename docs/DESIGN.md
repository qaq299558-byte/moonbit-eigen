# 设计说明：ABI 边界为什么这样切

> 本文回答一个具体问题：**MoonBit ↔ C++ 的这条线，为什么画在这里。**
> 接口契约见 [TYPE_MAP.md](TYPE_MAP.md)，踩坑见 [PITFALLS.md](PITFALLS.md)。

---

## 1. 约束：什么必须放在 C++ 侧

不是"想把 C++ 写薄"就能写薄的。有三件事**在 MoonBit 里无法完成**：

| 必须留在 C++ 的原因 | 具体表现 |
|---|---|
| **模板实例化** | Eigen 的 API 几乎全是模板（`Matrix<double, Dynamic, Dynamic>`、表达式模板）。C ABI 只能表达具体类型与函数，模板必须先在 C++ 侧落地成 `MatrixXd` 的具体运算 |
| **ABI 归一化** | Eigen 默认列主序；MoonBit 数组直觉是行主序。这个转换必须发生在能同时理解两侧约定的地方 |
| **生命周期桥接** | `new`/`delete` 与 MoonBit 的引用计数/finalizer 之间需要一座桥（`moonbit_make_external_object`） |

所以胶水层**不是**"为了方便而加的中间层"，而是这三件事的唯一落点。

---

## 2. 决定：胶水层只做这三件事，其余全部上移

反过来，下面这些**能放 MoonBit 就放 MoonBit**：

| 职责 | 放在哪 | 为什么 |
|---|---|---|
| 参数校验（维度、越界、长度匹配） | **MoonBit** | 在 MoonBit 侧做可以返回带上下文的错误信息；放在 C 侧只能返回状态码 |
| 错误信息组装与呈现 | **MoonBit** | 用户看到的是 `Result[T, String]` |
| 格式化输出（`to_string`） | **MoonBit** | 纯展示逻辑，没有理由下沉 |
| 运算前的形状检查（如乘法维度） | **两处都做** | MoonBit 侧给出友好错误；C 侧仍显式检查，因为不能依赖 Eigen 断言（release 下会被关掉） |
| 错误码 → `Result` 的映射 | **MoonBit** | 状态码不应泄漏给用户 |

### 2.1 这不只是口味问题 —— 它是验收要求

官方验收标准第 1 条：**"以 MoonBit 作为项目主要实现语言"**。

绑定类项目最容易在这里踩雷：如果实现集中在 C++ 胶水层，就有被判定
"这不是 MoonBit 项目"的风险。因此本项目的切分原则是：

> **C++ 侧只保留"MoonBit 做不到的事"，其余一律上移。**

这条原则同时带来工程质量上的好处（错误信息更友好、可测试性更好），
但它首先是一条**合规性**要求。

---

## 3. 错误传递：为什么不用 `nullptr`，也不用状态码出参

考虑过的三种方案：

| 方案 | 否决理由 |
|---|---|
| 返回 `nullptr` 表示失败 | MoonBit 侧把句柄绑到**抽象类型**，抽象类型没有 null 语义。拿到数值为 0 的句柄后，任何操作都是未定义行为，而且**崩在离出错点很远的地方** |
| 返回负状态码 + `Ref[T]` 出参 | 需要引入 `Ref[T]` 这层机制；调用方还要记得检查状态码，容易漏 |
| **错误哨兵 + 查询式错误信息**（采用） | 失败时返回一个**真实、可安全回收**的对象，只是 `valid == false`；MoonBit 侧用 `rows() == -1` 识别，用 `last_error()` 取原因 |

采用方案的具体形态：

```
C 侧                                    MoonBit 侧
──────────────────────────────────────────────────────────
valid=false, rows() == -1    ──────▶    Err(last_error())
正常矩阵,   rows() >= 0      ──────▶    Ok(Matrix)
```

**为什么"永远不返回 nullptr"很重要**：抽象类型的 null 是一个**类型系统看不见的坑**，
编译器不会帮你检查。把失败编码成"一个可以安全传递、安全回收、可查询的对象"，
就把这个坑消灭在 ABI 边界上。

---

## 4. 生命周期：为什么必须用 `moonbit_make_external_object`

C++ 侧 `new MatrixBox`，谁负责 `delete`？三种可能：

| 方案 | 问题 |
|---|---|
| 让用户手动 `destroy()` | 泄漏风险转嫁给用户；MoonBit 习惯上没有这个动作 |
| 在 C 侧登记全局互表，手动管理 | 重造轮子，且与 MoonBit 的回收时机不同步 |
| **`moonbit_make_external_object` 注册 finalizer**（采用） | 官方提供的机制：对象不可达时运行时自动调用 finalizer |

采用方案的三个要点（容易写错，见 PITFALLS §3）：

1. 返回给 MoonBit 的必须是**外壳对象**的指针，不是 `MatrixBox*`；
2. MoonBit 侧必须绑到**抽象类型**（`type EigenMatrix`），**不能**用 `#external`
   —— 否则内存管理系统会忽略它，finalizer 永不执行；
3. `finalize` **不得释放 `self` 本身**，只释放 payload 里的 C++ 对象。

**已知取舍**：依赖 GC 回收意味着 C++ 对象的释放时机不确定。
对数值计算场景可以接受（矩阵内存有界、不持有系统资源如文件描述符）。
若将来绑定持有稀缺资源的库（文件、socket、锁），应改为显式 `destroy` +
`#external type`，即放弃自动回收换取确定性。

## 5. 数据方向：为什么统一行主序

`Eigen::MatrixXd` 默认**列主序**。如果直接整块 `memcpy`，就会把 Eigen 的
存储约定泄漏到 MoonBit 侧，成为"本地测试全过、换个操作就错"的隐蔽 bug。

**采用方案**：所有搬运按 `(i, j)` 逐元素进行，对外统一行主序。

**代价**：小矩阵下可忽略；大矩阵下确有性能损失。
**为什么仍接受**：正确性优先于常数因子，且性能瓶颈在矩阵运算本身（Eigen 内部），
不在搬运环节。若未来搬运成为瓶颈，可改为"显式声明列主序的构造/导出变体"，
把约定变成 API 的一部分，而不是隐含行为。

---

## 6. 引用计数：为什么全部用 `#borrow`

官方文档明确：**默认语义正在从 `#owned` 迁移到 `#borrow`**。

本项目的所有非原始类型参数（`FixedArray[Double]`）都标了 `#borrow`，
因为 shim **只在调用期间读取、绝不保存指针**。

**这条判断的反面很危险**：如果哪天要让 C++ 侧长期持有 MoonBit 对象
（例如注册回调、把数组存进 C++ 容器），**必须去掉 `#borrow`**，
并按 owned 约定处理引用计数 —— 否则 GC 回收后 C 侧会拿到悬垂引用，
而这类 bug **不炸在出错点**。这也是把 ASan 放在第 1 周而不是最后的原因。

## 7. `moonbit_string_t` 的教训：只依赖有出处的 API

官方 2025-08 的黑板报教程用 `moonbit_make_string` 构造返回给 MoonBit 的字符串。
但该符号在**官方文档、官方 agent skill、GitHub issue 中均查不到出处**
（可能是内网/未文档化 API）。

**决策**：改用官方 agent skill 明确推荐的 `moonbit_make_bytes` + MoonBit 侧
`@utf8.decode_lossy`。

**这条决策的普适教训**：跨语言绑定里，**"某篇教程这么写"不等于"这个 API 存在"**。
只有出现在 API 参考或官方 skill 里的符号才值得依赖。
本项目的待验证清单（PITFALLS §8）就是这条原则的产物。

## 8. 构建方案：为什么准备 Plan B

官方把 `native-stub` 定义为 "**C** stub source files"，对 `.cpp` 无明文承诺。
生态里唯一的 C++ 绑定先例 `illusory0x0/qpainter` **根本没用 native-stub**，
而是用 `pre-build` + Makefile 编成静态库再链接。

| | Plan A（native-stub） | Plan B（预编译静态库） |
|---|---|---|
| 配置复杂度 | 低 | 高（多一套构建脚本） |
| 依赖 | 未被承诺的行为 | 有真实先例 |
| 失败后的代价 | 需要重做构建配置 | — |

**先试 Plan A，但预设 Plan B 与 10/19 熔断点**。
理由：Plan A 的配置成本几乎为零，值得先花 2 小时验证；
但不能把整个项目押在一个未被承诺的行为上。

## 9. 被否决的替代方案

| 方案 | 否决理由 |
|---|---|
| 用 MoonBit 重写线性代数（而非绑定） | 数值稳定性是几十年积累，重写等于放弃 Eigen 的全部价值；且 core 已有 `argparse` 的前车之鉴说明"重复造轮子"会被判不计入验收 |
| 绑定 Eigen 之外再顺带绑定 BLAS/LAPACK | 18 天单人做不完；Eigen 本身可选接 BLAS，属于 v2 |
| 通过 libclang 自动生成绑定 | 生态已有 `moonbindgen` / `moon-bindgen`；且自动生成器处理不了 Eigen 的表达式模板语义 |
| 把 MoonBit 编译成库给 C++ 调用 | native 后端**不支持**导出 `.dll`/`.so`（官方明确限制） |
| 用 MinGW g++ 作 native 编译器 | Windows 上官方**明确不支持** MinGW，且会拒绝包级非 MSVC 覆盖 |
